# Email — security & privacy model

## Threats and controls

| Risk | Control |
|------|---------|
| **Open relay / anyone sending as us** | The email-worker only sends on two authenticated paths. `/send` requires an `x-email-signature` HMAC over the raw body using `EMAIL_HMAC_SECRET` (shared only with the backend). `/auth-hook` requires a valid **Standard Webhooks** signature using `SUPABASE_AUTH_HOOK_SECRET`. Unsigned/invalid → `401`. Browsers can never reach the worker usefully. |
| **Auth-hook spoofing / replay** | Standard Webhooks signature verified with constant-time compare; timestamps older/newer than **5 minutes** are rejected. Hook disabled (503) when no secret is set. |
| **Forged unsubscribe / enumeration** | Unsubscribe links carry an HMAC token (`unsubscribeToken`) bound to the address; verified constant-time. A wrong token can't unsubscribe someone else or enumerate addresses. Like confirming, unsubscribing from the link takes two steps: `GET /api/newsletter/unsubscribe` only checks the link and shows a page with an Unsubscribe button (no script), and only the `POST` from that button unsubscribes, so a mail-security scanner fetching the welcome email's links can't opt a new subscriber out and delete their picks. The RFC 8058 One-Click `POST` (the `List-Unsubscribe-Post` header, sent by mail providers only on the person's request) still unsubscribes at once. |
| **Forged newsletter confirm** | The confirm token is signed by this server (`server/src/services/confirmToken.ts`): issue time + nonce, HMAC-bound to the address under `EMAIL_HMAC_SECRET`, compared constant-time. A token anyone else wrote into a row never confirms and is never re-sent. It expires `NEWSLETTER_CONFIRM_TTL_HOURS` after it was first issued (re-sending the same link never extends it), is single-use (cleared on confirm), and a link from before an unsubscribe never works again (unsubscribing clears it; the first request afterwards gets a fresh link, which later re-requests re-send). Confirming takes two steps: `GET /api/newsletter/confirm` (the link) only checks it and shows a page with a Confirm button that names the studios the click subscribes the address to, or, for a subscriber, the ones it adds; only the `POST` from that button subscribes the address, applies studio picks waiting on it, and lifts an earlier marketing unsubscribe. Mail-security scanners that fetch links can't opt anyone in or undo an opt-out. |
| **List exfiltration** | `email_log` and `email_suppressions` have RLS enabled with **no client policies** and `REVOKE ALL` from `anon`/`authenticated` — only the service role (server) can read them. `waitlist_signups` stays write-only for clients (existing design). Tokens are never returned to the client. |
| **Injection in templates** | All dynamic values are `escapeHtml`-escaped; URLs pass `safeUrl` (http/https/mailto only — `javascript:`/`data:` neutralised to `#`). Covered by `shared/email/templates.test.ts`. |
| **Auth-link hijack / account takeover** | The backend's auth emails (`/api/auth/email/*`) carry GoTrue `token_hash` links whose origin comes only from `APP_PUBLIC_URL` or the **exact** origins in `AUTH_LINK_ORIGINS` — never the CORS wildcard, which covers user-controlled `*.dreamstreamstudio.ai` preview hosts. A hostile `Origin` header is ignored. The raw `email_otp` is never mailed. |
| **Auth-email abuse / enumeration** | `/api/auth/email/*`: Turnstile (a sent token must verify; sign-up needs one unless it's a live-app sign-up holding a valid welcome ticket), 10 requests / 10 min per IP, and a durable per-recipient throttle in `email_log` (1/min, 5/h, 10/day). `/resend`, `/recovery`, `/magiclink` answer identically for unknown addresses and never create accounts. Logs mask addresses. |
| **Confirmation-email bombing (abuse-ops-11)** | `POST /api/interest` and `POST /api/newsletter/subscribe` (kind=updates) share `registerInterest` (`server/src/services/interestStore.ts`): Turnstile, one per-IP limiter for both (10 requests / 10 min, `interestRateLimit` in `index.ts`), and a durable per-recipient throttle on `newsletter-confirm`: none within 10 minutes of the last, at most 3 per day. It counts per inbox (`emailStore.inboxKey`: no `+tag`, and for Gmail no dots and googlemail.com = gmail.com), so `victim+1@gmail.com` … `victim+100@gmail.com` share one allowance instead of each getting its own. Other spellings that reach one mailbox are not folded together and each get their own allowance: any address on a catch-all domain, Fastmail subdomain addresses, protonmail.com/proton.me and Proton's own dot and hyphen variants, icloud.com/me.com/mac.com. The Privacy Policy says only that +tag and Gmail dot variants count as one address. The cooldown runs from the later of the last `email_log` send and the row's `confirm_sent_at`. If `email_log` can't be read, no confirmation email is sent until it can (the limits per inbox live only in the log, and each alias has its own row, so reading nothing would let every alias send); the answer is the same 200 `pending`. Nor is one sent when its `queued` row can't be written to `email_log` (`mailer.sendEmail` refuses public-form mail it can't log: these per-inbox limits, the public-form share and the hard caps all count logged sends only, so unlogged sends would escape every one of them); that request is answered as a failed send is (below). Before mailing, a request claims the inbox (an in-memory claim per `inboxKey`, taken with no await after the throttle's read and held until the send is logged or has failed) and then the row (a conditional update on `confirm_sent_at`), so parallel requests send one email, also when each names a different alias of the inbox (`victim+1@…`, `victim+2@…`: each alias has its own row, so the row claim alone let each of them send). The inbox claim is per backend instance; production runs one (a single `Backend` container), and with several, parallel aliases could get one email per instance. A failed or capped send gives both claims back. Unauthenticated public-form mail (`newsletter-confirm` and the early-access receipt `access-requested`, together: `emailStore.PUBLIC_FORM_EMAIL_TEMPLATES`) may use only half of `EMAIL_MAX_PER_DAY` and of `EMAIL_MAX_PER_MONTH` (`CONFIRM_EMAIL_BUDGET_SHARE`), so unauthenticated requests can't use up the capacity sign-in, recovery and invite mail need. The early-access receipt goes at most once a day per inbox (`interestStore.claimAccessReceipt`, the same inbox key and claim), and not at all while public-form mail has used its share or the mailer is capped, or while `email_log` can't be read or its row can't be written; the request is stored and answered the same way either way (the Privacy Policy says we usually email a receipt, and names both limits). No unauthenticated path puts a caller-supplied name into an email (`/subscribe` ignores `firstName`): the email goes to whatever address the caller typed. A re-request inside the window re-sends nothing; a still-valid link is re-sent as is. A `confirm_sent_at` in the future (only the old all-column client INSERT grant could write one) is ignored, so a planted row can't block an address's confirmation email. Confirm links are built from `EMAIL_PUBLIC_BASE_URL` / `APP_PUBLIC_URL`, never the request's `Host` header. Mailer logs mask addresses. |
| **Interest list exposure / subscription oracle** | Anyone can type anyone's address, so `POST /api/interest` gives every valid request the same `200 {status:'pending'}` answer and echoes only the studios that request picked: it never says whether the address is new, pending, subscribed, unsubscribed or throttled, and never returns stored picks (the old `/subscribe` answers the same way for kind=updates; its request-access path still says "already on the list", "you already have an account" or "you already have access" by design, behind Turnstile, and the Privacy Policy says so; its account check is an exact, case-insensitive match, never a pattern, so `*@company.com` can't ask whether anyone there has an account). Every valid request also gets the same answer when the mailer itself is capped (`interestStore.mailerCapReached`, checked with the budget before anything about the address; otherwise only the sends would fail, which would tell a throttled address from one that isn't), and a request that sent nothing and one that sent the email are held to the same time (`interestStore.holdAnswer`: at least `ANSWER_FLOOR_MS`, 2 s, from the instance's first request, or, while recent sends took longer, the 95th percentile of the sends in the last hour (`SENT_SAMPLE_WINDOW_MS`, at most 50 of them, and the newest send however old it is), counting sends up to the mailer's own timeout), so response time doesn't tell them apart while sends take about as long as each other, also right after the container wakes or a deploy restarts it. With fewer than 20 sends in that hour the hold is the slowest of them, so a slow send keeps every answer that slow until it is an hour old and a newer send has come (or 19 more sends have come); an hour with no sends doesn't drop the hold back to the floor. A sending request's own time counts before its answer is held, so it raises the hold for the answers after it, but its own answer still takes as long as its send did. Known residuals: (1) a send slower than the hold at that moment answers later than a throttled request at that moment would, once sends take longer than the 2 s floor (a slow email worker): the first send after the container wakes or a deploy restarts it (nothing is held above the floor yet), a send slower than the newest one and every one in the last hour, and, with 20 or more sends in the hour, where the hold leaves out the slowest 5% (it is the 2nd or 3rd slowest), about one send in 20. A caller can learn the hold by first probing an inbox of their own that is already throttled; a victim's answer that then takes longer says a link went out (and that probe emailed the victim). And because a send's time is counted before its own answer, a slow one also raises the hold for the answers after it, which a request made right after it can see. (2) The mailer counts its cap again at send time, several round trips after `mailerCapReached`, and counts only sends already logged as sent. A request in flight at a day's (or month's) cap boundary can pass `mailerCapReached` and then be refused by the mailer (`503 email_unavailable`) when other sends finishing during its round trips reach `EMAIL_MAX_PER_DAY` (or `EMAIL_MAX_PER_MONTH`), while a throttled request at that moment answers `200 pending`. That can hit several requests at one boundary, and the count at their check need only be within the number of sends then finishing, not exactly one under; it needs public-form mail still under its half while the whole cap is reached, so at least half of `EMAIL_MAX_PER_DAY` in other mail that day (100 by default) or, at the month's boundary, at least half of `EMAIL_MAX_PER_MONTH` in other mail that month (1,250 by default, however little was sent that day), and the count isn't visible to callers. Requests that reach the mailer's check at the same moment can also all pass it, so a day can end a few sends over the cap. A send that fails for another reason (the email worker down, or its row in `email_log` can't be written) still answers `503 email_unavailable` to that request only. An unauthenticated request never changes a subscriber's picks: new ones wait in `metadata.pending_interests` until they press Confirm, and the Confirm page names them first. The page's form carries the studios it named (field `s`), and the click applies exactly those: if more were registered for the address after the page opened (a stranger can do that, and a throttled request keeps the same link), nothing changes and the page is shown again with the current list (`emailStore.confirmSubscriber` → `'changed'`). The click's write is guarded on the row as it read it (`emailStore.guardOnRead`, the same guard as the picks' own writes), so a registration that lands between the click's read and its write is neither confirmed nor lost: the page is shown again and names it. Picks are written with a conditional update on what was read, so parallel requests for one address keep every request's picks. The condition compares only server-decided values (the picks, the subscribed state and `metadata.pending_interests`, each only while it has the shape the server writes: a short list of short strings), never the whole client-writable `metadata`: a planted value JavaScript can't hold exactly (a 20-digit number) would never compare equal, and a planted list of thousands of picks would outgrow the request URL, so every update to that address would fail. A value of any other shape is not compared and is replaced by the cleaned list whenever the update writes that field. An existing row's note is never replaced, and an existing request-access row only gains picks. The confirm link never reveals state to anyone but the holder of a valid signed token. Clients can't read `waitlist_signups` (no SELECT/UPDATE/DELETE). **The table itself still answers until `server/sql/register_interest_2026_11.sql` is applied:** a client's direct INSERT of a listed address fails with 23505 (PostgREST 409) on the unique index `idx_waitlist_email_kind`, so the public anon key can test whether an address has a row, and anon/authenticated can INSERT any column (both verified live 2026-11-05). The form's offline fallback (`services/waitlist.ts`) already answers a duplicate exactly like a new signup. That file limits client INSERT to `email, kind, source, metadata` with a policy requiring a lowercase address and default values (no "confirmed" row, no planted picks or timestamps) and a `metadata` object of at most 8 KB without the server's `pending_interests` key, and its trigger `waitlist_client_insert` writes each client row that passes that policy itself, with `ON CONFLICT DO NOTHING`, so a listed and an unlisted address get the same 201; a row that fails the policy is refused the same way for both. The server already ignores tokens it didn't sign and future `confirm_sent_at` values. The admin summary (`GET /api/admin/interest/summary`, `requireAdmin`) returns counts per studio only — no address, token or note. Retention, once that file is applied (pg_cron `waitlist_interest_retention()`, daily): unconfirmed rows are deleted 30 days after their last confirmation email, unsubscribed rows 30 days after unsubscribing (unless they asked again), and `email_log` rows of `newsletter-confirm` mail once they are more than 30 days old and from before the current UTC month (the monthly email cap and the confirmation budget count this month's), whoever they went to; a timestamp in the future never keeps a row. Unsubscribing clears the studio picks (including waiting ones) at once. The marketing suppression list is kept: it is what stops us emailing an address that opted out. Before the file is applied none of this retention runs. |
| **Spend abuse / runaway cost** | Hard caps (`EMAIL_MAX_PER_DAY` / `EMAIL_MAX_PER_MONTH`, default under the free tier) checked before every send against the sends already logged as sent (public-form mail whose row can't be written isn't sent; other mail, such as sign-in links, still goes out then, uncounted); a send the check refuses is skipped + alerted, never delivered. Sends that reach the check at the same moment can each pass it, so the count can end a few over a cap (by at most the sends in flight together). Per-route rate limits apply (`systemRateLimit`). |
| **Forged sign-in alerts** | `POST /security` (new-sign-in alerts from the Supabase access-token hook, ADR 0006) requires an `x-ds-signature` HMAC-SHA256 over `"<t>.<payload>"` with `SECURITY_HOOK_SECRET` (shared only with Supabase Vault and the live Worker), ±5 min; 503 when the secret is unset. IPs arrive already masked and are masked again; the "Not you?" link carries a one-time token whose SHA-256 is all the database keeps. |
| **Secrets** | `EMAIL_HMAC_SECRET`, `SUPABASE_AUTH_HOOK_SECRET` and `SECURITY_HOOK_SECRET` live as Worker secrets (and, for the backend's copy of `EMAIL_HMAC_SECRET`, D1 `backend_env`), never in the repo. `.env*` is git-ignored (only `.env.example`). Rotation order: `docs/infrastructure/live-security-runbook.md` §1. |

## Essential vs marketing (compliance)

Templates are classified in `shared/email/templates.ts` (`TEMPLATE_KIND`):

- **essential** — account/security/transactional (`auth-*`, `welcome`, `signin-alert`,
  `access-requested`, `newsletter-confirm`, invites), plus `announcement`, the notice our team
  composes in the admin console and can send to any pasted list of addresses (a launch or other
  promotion belongs in the marketing `product-update` template instead). Always sent; **no
  unsubscribe** (shown as a "required notification" footer line); bypasses the suppression list.
  The Privacy Policy's Emails section says so.
- **marketing** — opt-in (`newsletter-welcome`, `product-update`). Carries a working
  unsubscribe link **and** an RFC 8058 `List-Unsubscribe` / `List-Unsubscribe-Post` header for
  native one-click unsubscribe in Gmail/Apple Mail; **honors the suppression list**.

The mailer refuses to send a marketing message if it can't build a working unsubscribe link
(missing `EMAIL_PUBLIC_BASE_URL`), so we never send non-compliant marketing mail. Every email
carries the honest "why you're getting this" footer + sender postal address (CAN-SPAM / CASL).

## Read receipts / open tracking — privacy note

Marketing **and** essential mail can embed a 1×1 open-tracking pixel
(`/api/email/o/:id.gif` → stamps `email_log.opened_at`). This is **best-effort**: many clients
block remote images or pre-fetch them, so opens are a weak signal, not proof of reading. The
pixel only records the open timestamp against our own log row — no third-party tracker, no
profile, no cross-site cookies. To disable tracking entirely, leave `EMAIL_PUBLIC_BASE_URL`
unset (no pixel URL is generated) or strip `params.pixelUrl` in the mailer. Mail that carries a
one-time link sends no pixel (`track: false`): the auth emails and the double opt-in
`newsletter-confirm`.

## Bot protection — Cloudflare Turnstile

Turnstile guards the public, abuse-prone entry points. **Fully dormant until keys are set** —
no widget renders and no endpoint is gated, so nothing changes for anyone until you turn it on.

- **Where:** the auth form (`AuthPage` → sign-in via Supabase `captchaToken`; sign-up /
  magic-link / password-reset / resend via `/api/auth/email/*`, verified server-side, with the
  old Supabase call as the fallback) and the public newsletter / request-access form
  (`WaitlistForm` → `/api/newsletter/subscribe`, verified server-side).
- **Client:** `components/Turnstile.tsx`, gated by `VITE_TURNSTILE_SITE_KEY`. Tokens are
  single-use; the widget resets after every attempt.
- **Server:** `server/src/services/turnstile.ts` verifies tokens against Cloudflare's
  siteverify, gated by `TURNSTILE_SECRET_KEY`. **Fails open when unconfigured** (no gate),
  **fails closed when configured** (a network error during verification denies the request).

**Owner setup:** create a Turnstile widget in the Cloudflare dashboard → set
`VITE_TURNSTILE_SITE_KEY` (client) + `TURNSTILE_SECRET_KEY` (server) → and enable Turnstile in
**Supabase → Authentication → bot/abuse protection** so the auth `captchaToken` is validated.

## Failure posture

The mailer **never throws** and email is **best-effort**: a down worker, missing config, or
hit cap returns a structured `{ ok:false, skipped|error }` and is logged — it never blocks a
signup, a confirm, or an API response.
