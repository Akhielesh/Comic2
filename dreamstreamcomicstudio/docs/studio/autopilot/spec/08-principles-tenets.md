# 08 — Product Principles & Design Tenets

> Part II · Product Definition · Canon: [SPEC-INDEX](../SPEC-INDEX.md)

## 8.1 How to read this

These are the rules every later section, feature, and pull request is measured against. They are
not aspirations — they are **decision criteria**. When two designs are otherwise tenable, the one
that better satisfies these principles wins; when a design violates one, it is rejected or
re-scoped, not shipped with a TODO. Each principle below states **what it means in practice** and
gives an **anti-example** (a real-feeling shortcut we explicitly refuse) so the line is
unambiguous. The product tenets restate and operationalize the seven non-negotiables from
[01-vision-positioning.md §1.5](./01-vision-positioning.md); the engineering, design, and autonomy
tenets make them buildable.

The quality bars here are stated at altitude. Their numeric thresholds, SLOs, and gates live in
Part IV ([37-reliability-sre](./37-reliability-sre.md), [39-performance-scalability](./39-performance-scalability.md),
[43-testing-strategy](./43-testing-strategy.md)) and are referenced, not duplicated, here.

## 8.2 Product principles

**P1 — Brakes before engine.** Every autonomy capability ships *after* the governance that
contains it — a budget cap, a checkpoint, an audit record, and a kill switch — exists and is
tested. Safety is a feature with its own acceptance criteria, not a hardening phase bolted on
later. In delivery terms this is why the backlog sequences A0–A2 (brakes + control plane) before
A4–A5 (real build + deploy) and why `VENTURES_ENABLED` defaults off.
*Anti-example:* shipping the autonomous build loop first "to demo the magic," with budgets "coming
in the next sprint." That is exactly how a platform wakes up to a five-figure cloud bill.

**P2 — Code-optional, never code-locked.** The default experience needs no editor — ~90% of users
should reach a live, improving product without opening code. The 10% who want it get the real
multi-file source, GitHub sync, and full manual takeover, at any moment, with no "export tax" or
degraded copy.
*Anti-example:* a hosted-only sandbox whose "export" produces a tarball that doesn't build outside
the vendor, or an editor that's read-only while the agent "owns" the repo.

**P3 — Honest by construction.** The product always shows what it's doing, what it costs, what
it's unsure about, and what it could not verify. No fake previews, no hidden spend, no silent
failures, no green checkmarks for steps that were skipped. Uncertainty is surfaced, not smoothed
over.
*Anti-example:* rendering a "preview" screenshot generated by the model instead of the actual
running build; reporting "deployed" when only the build step passed.

**P4 — Your cloud, your keys, your data.** BYO provider accounts, BYO model keys, and a portable
system-of-record (Supabase) are first-class. Managed mode exists for speed and instant previews,
never to trap the user. Anything created in managed mode must be migratable to the user's own
accounts.
*Anti-example:* storing the only copy of a venture's source and deploy config in proprietary
managed infra with no path to the user's GitHub and Cloudflare.

**P5 — Continuous, not frantic.** "Always-on" is a governed heartbeat (a Durable Object Alarm
cadence) bounded by budgets and a no-progress detector — not a hot loop burning tokens. The
system does meaningful work on a tick, then rests; idle ventures cost ~nothing.
*Anti-example:* a `while(true)` agent that re-plans every few seconds, racking up model spend with
no shipped change to show for it.

**P6 — Reuse over rebuild.** The platform is orchestration + governance layered over assets that
already work (the agentic build loop, the swarm, the container sandbox, Nango, Stripe metering,
GitHub sync, the `studio_*` data model). We extend the existing repo; we do not re-implement
proven machinery to make it "ours."
*Anti-example:* writing a new billing/metering subsystem when Stripe + usage metering already ship,
or a parallel sandbox runtime alongside `studio-worker/`.

**P7 — Enterprise-grade by default.** Observability, multi-tenancy isolation, testing, and
security are foundations (the F-series), present from the start of any surface — not features sold
to a future "enterprise tier." A solo founder gets the same isolation and audit trail an org does.
*Anti-example:* shipping per-venture features that share state across tenants "for now," planning
to add RLS once there's a paying enterprise customer.

## 8.3 Engineering principles

**E1 — Additive and flag-gated.** New capability is added behind a flag (`VENTURES_ENABLED` and
finer-grained sub-flags) and changes nothing for existing Chat/Comic/Studio users until explicitly
enabled. Prod behavior is unchanged until the owner flips a switch.
*Anti-example:* editing a shared code path "while we're in here" so existing users see new behavior
the moment the branch merges.

**E2 — Small, reversible steps.** Work lands in increments that can each be reverted cleanly. A
change that can't be backed out without a data migration or a manual cleanup is decomposed until it
can — or it carries an explicit, tested rollback.

**E3 — Durable state survives restarts.** Anything an autonomous run depends on lives in durable
storage (Durable Object state, Workflows, Supabase) — never only in process memory. A Worker
eviction, a deploy, or a crash mid-run must be resumable from the last committed checkpoint, not
lost.
*Anti-example:* holding a venture's in-flight plan in a module-level variable that vanishes on the
next isolate recycle.

**E4 — Idempotency everywhere it matters.** Loop ticks, webhooks, deploys, and billing events are
designed to be safely retried. Re-delivering the same event or re-running the same tick produces
one effect, not two. Every externally-triggered or auto-retried operation carries an idempotency
key.
*Anti-example:* a deploy adapter that charges twice or ships twice when Workflows retries the step.

**E5 — Observability-first.** Instrumentation (structured logs, metrics, traces, the per-venture
activity stream) is written *with* the feature, not after an incident. A feature that can't be
observed in production is not done.

**E6 — Tests as a gate, not a courtesy.** New code ships with tests; the verify suite
(`npm run typecheck && npm run build:server && npx vitest run && npm run build`) must be green
before commit. A red suite blocks the commit — there is no "fix the test later."

**E7 — Secrets only in Nango / env.** BYO credentials live exclusively in Nango; platform secrets
live in environment configuration. Secrets are never committed, never logged, never printed, and
never returned in an API response or activity event.
*Anti-example:* echoing a connected account's token into a debug log line.

**E8 — Never force-push production; never destroy owner data.** Production (`Dreamstrream-v1`) is
fast-forward/merge only. Existing tables and user data are never deleted or overwritten. Schema
changes are additive and migration-gated. Anything that would touch production data or spend money
is a human-gated decision per [OPERATING-MODEL](../OPERATING-MODEL.md).

## 8.4 Design / UX principles

**D1 — Legibility of autonomy.** A user must always be able to understand what the agents are
doing and why, in plain language. The autonomous loop's reasoning ("show your work") is surfaced as
a readable trace, not a wall of raw logs. Autonomy people can't read is autonomy they won't trust.

**D2 — One-glance status.** Every venture has a status that a user can read in under two seconds:
building / awaiting approval / shipped / paused / blocked / over-budget-soon. The Operator Console
is designed so the owner can answer "is everything OK?" without drilling in.

**D3 — Approvals are one click, with context.** A checkpoint presents the decision, the *why*, the
diff/impact, and the cost — then resolves in a single click (approve / deny / adjust). The user
never has to leave the approval to go find what they're approving.
*Anti-example:* an "Approve deploy?" prompt with no diff, no target, and no cost shown.

**D4 — Show cost, always.** Spend is visible everywhere a decision is made: the budget meter on the
console, the cost on every checkpoint, the running tally per venture. There is no screen where the
user is spending money blind.

**D5 — Progressive disclosure.** The default surface is calm and minimal (status, approvals,
spend); depth (logs, traces, raw config, the code editor) is one click away for those who want it.
The non-technical founder and the power developer use the same product at different depths.

**D6 — Reduced motion respected.** The live activity stream and build animations honor
`prefers-reduced-motion`; nothing essential is conveyed by motion alone. Animation is decoration,
never the only signal.

**D7 — Mobile-first for monitoring.** The most common real-world job — *check status, approve a
checkpoint, pause if needed* — must be excellent on a phone. Building is desktop-leaning; watching
and steering is mobile-first, because that's when the user is away from their desk and the loop is
running. (Full treatment: [19-mobile](./19-mobile.md).)

## 8.5 Autonomy / safety principles

**S1 — Default to ask on irreversibles.** Anything destructive, anything that spends money beyond
the agreed budget, anything that touches production data, and anything that changes existing-user
behavior defaults to a checkpoint. The agent proposes; the human disposes. Reversible, in-scope,
in-budget work proceeds without asking — that's the point of autonomy — but the irreversible class
is ask-first by default.

**S2 — Budgets are hard, not advisory.** A budget is a ceiling enforced by the runtime, not a
suggestion the agent weighs. When a venture reaches its cap, the loop stops and asks — it does not
"finish the current task" past the line. Spend cannot exceed what the user set.
*Anti-example:* a "soft" budget that warns at 100% but keeps spending while it "wraps up."

**S3 — Scope guard.** An autonomous run acts only within the venture's approved roadmap and
declared scope. Work that drifts outside scope (a new dependency class, a new provider, a schema
change to a shared table) is a checkpoint, not a silent expansion.

**S4 — No progress → ask, don't loop.** A no-progress detector watches for ticks that spend
without shipping a verifiable change (repeated failures, flapping, re-planning the same goal). On
detection the loop pauses and asks for help rather than burning budget in a circle. Stuck is a
state we surface, not one we hide behind retries.

**S5 — Full auditability.** Every autonomous decision, checkpoint, spend event, deploy, and
state change is recorded in an append-only audit trail tied to the venture and the actor (which
agent, which run/tick). "What did it do and why, last Tuesday at 3am?" must be answerable from the
record alone.

## 8.6 Definition of Done

Two distinct definitions apply — one for *us building Autopilot*, one for *Autopilot building a
user's product*. They are deliberately the same shape (build → verify → ship → record), mirroring
the two loops described in [OPERATING-MODEL](../OPERATING-MODEL.md).

### 8.6.1 DoD for a platform feature

A feature is **Done** when all of the following hold:

1. **Built additively and flag-gated** — no behavior change for existing users until enabled (E1).
2. **Tested** — unit/integration tests cover the new behavior and its failure modes; the four
   verify commands are green (E6).
3. **Observable** — structured logs, the relevant metrics, and (where user-facing) an activity
   event exist and were confirmed emitting (E5).
4. **Safe** — secrets handled per E7; no destructive or prod-touching action without a checkpoint
   (S1); reversible or carrying a tested rollback (E2).
5. **Accessible & responsive** — meets the a11y bar (§8.7) and works on mobile for any monitoring
   surface (D7).
6. **Documented** — STATUS, CHANGELOG, OWNER-ACTIONS, and the relevant spec/section updated so docs
   don't drift from code (per [AGENTS](../../AGENTS.md)).
7. **Acceptance criteria demonstrably met** — with a one-line proof in STATUS.
8. **Shipped** per the owner's shipping rule, with no red suite and no force-push.

### 8.6.2 DoD for an autonomous Goal

A *Goal* (a backlog item the agents own) is **Done** when:

1. **Code change is real and committed** to the venture's repo (not just proposed).
2. **Build passes** in the container sandbox; tests for the venture pass where they exist.
3. **Preview verified** — the change is observable in a real running preview, not a model-rendered
   mockup (P3).
4. **Within budget** — the goal completed under its budget; spend is recorded.
5. **Deployed if in scope** — to managed/BYO target, *with a checkpoint cleared* if the target is
   production (S1).
6. **Audited** — the goal, its ticks, decisions, cost, and resulting deploy are in the audit trail
   (S5).
7. **Reflected** — outcome (shipped / blocked / escalated) is written back to the roadmap/backlog
   so the next tick starts cold and correct.

A goal that "looks done" but failed any of these is **blocked** or **escalated**, never silently
marked complete.

## 8.7 Quality bars (high level; detail in Part IV)

These are the minimum bars every shipped surface must clear. Thresholds are owned by Part IV.

- **Performance.** User-facing surfaces feel instant; the Operator Console and activity stream
  update in near-real-time without jank. Targets (initial load, interaction latency, stream
  freshness) are set in [39-performance-scalability](./39-performance-scalability.md). Idle
  ventures consume negligible compute (P5).
- **Accessibility.** Targets **WCAG 2.2 AA**: keyboard-operable, sufficient contrast, labeled
  controls, reduced-motion honored (D6), screen-reader-legible status and approvals. Full
  spec: [20-accessibility](./20-accessibility.md).
- **Test coverage gate.** New code ships with tests and the verify suite stays green (E6). The
  coverage gate, critical-path requirements, and the autonomy test harness are defined in
  [43-testing-strategy](./43-testing-strategy.md).
- **Reliability.** SLOs, error budgets, and the resumability guarantees that back E3/E4 live in
  [37-reliability-sre](./37-reliability-sre.md).

## 8.8 Anti-patterns we explicitly reject

- **Ungoverned autonomy.** No budgets, no checkpoints, no kill switch — "trust the agent." We
  reject it as a design, not just a default (P1, S1, S2).
- **Fake honesty.** Model-rendered previews, optimistic status, hidden spend, silent failures (P3).
- **Lock-in dressed as convenience.** Managed-only storage of source/config with no real export
  path (P2, P4).
- **Hot-loop autonomy.** Spending tokens on a tight re-plan loop with nothing shipped (P5, S4).
- **Big-bang, irreversible changes.** Large unflagged merges that alter existing-user behavior or
  can't be rolled back (E1, E2).
- **In-memory durability.** Run state that doesn't survive a restart (E3).
- **Secrets in logs / responses / commits.** Any path where a credential leaks (E7).
- **Force-pushing production or destroying owner data.** Non-negotiable (E8).
- **"Enterprise later."** Treating multi-tenancy, isolation, observability, or security as a tier
  to upsell rather than a default to ship (P7).
- **Approvals without context.** Asking a human to approve something they can't see the cost,
  diff, or impact of (D3, D4).

> These principles are load-bearing: a later section that proposes a feature in conflict with one
> of them is, by definition, wrong about the feature — fix the feature, not the principle.
